# Pixelworks Iris5 – GitHub Actions experiment (Stage 17)

The default `audit` workflow verifies the stage16 763/763 CRC reference and the exact upstream source commits. It does not compile the kernel or flash anything.

Use a new GitHub repository owned by you. The starter includes only `Module.symvers` provided by japq7s, the original kernel's IKCONFIG and stage16 CRC reference CSV, plus new CI code. **Do NOT upload `build-scripts.zip`: it contains a test RSA private key and build-images.sh is unnecessary here.**

1. Upload all files, **preserving `.github/workflows/iris5-build.yml`** and the `ci/` tree, to the repository's default branch (often `main`). You can upload folder contents using `git`, GitHub web uploader, or GitHub Desktop. Prefer a private repository for these analysis artifacts.
2. Open **Actions → Iris5 6.6.139 - preflight / experimental foundation → Run workflow**.
3. Leave `phase=audit`, then run. It should finish after network fetch + audit checks. Download the attached `iris5-stage17-audit-*` artifact and share logs/results.
4. Only after reviewing the audit and runner resources consider `phase=foundation`. This can consume substantial build time/disk and may fail on GitHub's standard runner. It is **not** an external Display module build, and does not bypass CFI, symbol versions, signatures, or BTF checks.

## What this is NOT

- No patched `msm_drm.ko` is generated by audit. Foundation attempts only the kernel Image/in-tree modules and checks 739 imported kernel CRCs if it reaches completion.
- The external seven Qualcomm/Oplus provider Module.symvers are still missing; Display baseline is a later, separate phase.
- The official toolchain source is pinned to the Android 15 release **branch** rather than a fully attested author build commit. The CI records the resolved commit and checks actual compiler fingerprint; it does not prove byte-identical toolchain provenance.
- Generated `.config` must match original IKCONFIG; do not overwrite it to force a passing build.
- No phones/ADB/AnyKernel/boot or vendor image packaging, KernelSU patch, or runtime experiments.
- Ubuntu 24.04 packages currently ship pahole **1.25**, while the original reference specifies **1.27**. Thus the heavy `foundation` phase is expected to stop at the version gate on an unmodified standard runner. We will need a verified 1.27 installation in a later revision; do **not** bypass the version gate. Other possible blockers: toolchain source availability, RAM/disk limits and source/config differences. The first run should use `audit` only.
